One date/time service, and fix the 5:30 that came from date-only values

Every captured task showed a wrong time - always the same wrong time, across
text, voice and picture. They all failed together because they converge on one
line, not because three parsers were each broken.

DATE_TIME in model.js is now the only place that converts between the three
conventions the app was mixing: dueDate as a UTC ISO string, created as an
ordering number, due_at as the database column. Stored is always UTC, displayed
always through the local-reading helpers, and every datetime-local value goes
back through fromDateTimeLocal rather than the Date constructor.

The 5:30, corrected. I first assumed a datetime-local value was being read as
UTC. It is not - a date-TIME string is read as local, and a probe check disproved
that theory before it was committed. The real cause is a date-ONLY string:
new Date("2026-10-05") is defined by the spec as UTC midnight, which in Kolkata
is 05:30. Because the offset is fixed it looked like a default rather than a
fault, and every capture that named a date without a time inherited it.
fromDateInput now builds local midnight explicitly, and the probe asserts both
directions - that the old path really does yield 5:30 here, and that the new one
does not - so it cannot pass on a machine where the two happen to agree.

Three real fixes: the edit dialog was slicing a UTC ISO string into the datetime
box and saving it straight back, so it displayed UTC as if it were local; the
capture save path and the time-only slot resolver used the same round trip.
localDayKey replaces toISOString().slice(0,10) for local day keys, which was the
UTC date - the previous day here until 05:30.

created, due and reminder stay three separate facts. created is an ordering key
compared with < in both client and API, so it stays a number; dueDate is an
instant; the reminder lead is derived from dueAt and recomputed when it changes,
so a re-dated task cannot keep a stale reminder time.

datetime-probe.mjs runs the page under a forced timezone - Kolkata, and Los
Angeles for an offset in the opposite direction - because a test at UTC+0 cannot
catch this: at zero offset the broken path and the correct path agree exactly.
9 checks, both zones. 32 of 32 suites pass.
